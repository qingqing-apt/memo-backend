## 二、基线结果（优化前，第三天代码）

**用例通过：10/12**，工具调用正确 **4/5**，平均耗时 1.75s。

功能虽然基本都过，但暴露了 **5 个具体问题**：

| 用例 | 场景 | 基线表现 | 问题类型 |
| ---- | ---- | ---- | ---- |
| C07 | 信息不足（"帮我找一下那个东西"） | 追问了，但**一次性列出全部 4 条** | 回答质量 |
| C08 | 超范围（"帮我删掉这条"） | 说明了只读边界，但**多余调用 `search_my_memos`** | 工具选择 |
| C09 | 工具异常（模拟 DB 故障） | 报错正确，但**同一工具被重复调用 2 次**（3 次重复均复现；单次全量运行未复现，属**不稳定问题**） | 重试策略 |
| C11 | 工具层：空关键词搜索 | **返回全部 4 条**，等同把全量内容当「命中」 | 工具参数校验 |
| C12 | 工具层：数据库异常 | 异常**直接抛到上层**，未被兜底 | 错误处理 |

> 工具正确率 4/5 是被 C08 拉低的（期望不调用工具，实际调用了）。

## 三、问题分析与改动

五个问题分属两类根因，因此**按任务要求分两轮改、每次只改一类因素**，便于归因。

### 优化 A：Agent 指令（回答质量 / 工具选择 / 重试）

根因：`AGENT_INSTRUCTIONS` 只写了能力范围和安全约束，**没写「按场景怎么交互」**。

| 问题 | 原因判断 | 改动（新增交互规则） |
| ---- | ---- | ---- |
| C07 | 指令未说明「信息不足先追问」 | 规则 7：请求含糊时先用一句话追问，不要一次性列出全部 |
| C08 | 指令未说明「写入类请求直接拒绝、不必确认」 | 规则 8：要求修改/删除时直接说明只读、不调用任何工具 |
| C09 | 指令未说明「工具报错不要立刻重试」 | 规则 9：工具报错时不重复调用，直接说明失败并建议稍后重试 |

落点：`app/agent/memo_agent.py` 的 `AGENT_INSTRUCTIONS`，新增 3 条「交互规则」。

### 优化 B：工具层（参数校验 / 错误返回 / 输出上限）

根因：工具把「模型传什么就执行什么」当默认，**校验和兜底完全依赖模型自觉**——而任务要求「安全措施不能只依赖系统提示词，关键参数范围必须由后端代码校验」。

| 问题 | 原因判断 | 改动 | 落点 |
| ---- | ---- | ---- | ---- |
| C11 | `keyword=""` 时 SQL 变成 `LIKE '%%'`，命中全表，看起来像「搜索成功」 | 工具层校验：`strip()` 后为空直接返回「参数不合法：缺少搜索关键词」，不查库；长度 > 50 也拒绝 | `app/agent/tools.py` |
| C12 | 数据库异常直接向上抛，由框架转成错误结果交给模型，错误形态不可控 | 新增 `_safe_query()` 统一兜底：捕获异常 → 返回带错误码的固定文案（`DB_UNAVAILABLE`），完整异常只写服务端日志（不含用户数据） | 同上 |
| C09（第二道防线） | 只在指令层约束，模型仍有概率再试 | 工具层返回明确「不可用」文案，让模型没有「再试一次可能成功」的动机 | 同上 |
| — | 输出无上限，数据量大时会把整表塞进上下文 | 单条内容截断 200 字、单次最多 20 条，并提示「仅显示最近 N 条」 | 同上 |

同时收紧了工具描述（`search_my_memos` 明确「keyword 必填、用户没给关键词就先追问、禁止空字符串搜索」），让模型更容易选对工具。

## 五、未采用方案与无效改动

- **未采用：在工具层硬性拦截重试次数**。agent-framework 的重试由模型驱动，工具每次调用都是独立执行，工具层无法区分「模型重试」和「用户再问一次」，硬计数会误伤正常查询。最终采用「指令约束 + 明确错误文案」双保险。
- **无效改动（如实记录）**：单条 200 字 / 最多 20 条的输出上限，在当前 4 条虚构数据下**从未触发**，未观测到任何指标变化。保留作为防御性改动，但不能算作有实测收益的优化。

## 六、限制与未解决问题

1. **检查逻辑依赖关键词匹配**：开发中曾出现 3 次误判（把"哪一条"当没追问、把"未能完成"当没说明失败），说明纯关键词判定鲁棒性有限，不是语义级判断。
2. **样本量小**：12 个用例只覆盖主要场景，不能代表全部真实使用。
3. **模型随机性**：只对关键用例做了 3 次重复；C09 就是不稳定问题的例子——单次全量运行没复现，靠重复才确认。
4. **前端未改动**：Agent 失败时的前端提示沿用 CopilotKit 默认行为，未做定制；因此本次不提供前端状态截图。
5. **容器复现未验证**：本机无 Docker，容器配置已写但未实测。
6. **C11/C12 是工具层单测，不是端到端**：它们验证的是代码校验逻辑，不能替代「用户在界面上提空关键词」的真实链路验证。

## 八、复盘

- **最有价值的一项优化**：优化 B 的空关键词校验。它表面上只是「参数校验」，实际堵的是一个**越权读取全量数据**的口子——模型只要传空关键词，就能把用户全部备忘当「搜索结果」拿到。安全收益大于质量收益。
- **一个未解决问题**：评测判定仍靠关键词匹配，不是语义判断，遇到表达变体容易误判，这是当前评测体系最该改的地方。
- **一次未达预期的经历**：第一次给 C07 优化后复测反而判失败，排查发现不是 Agent 退化，而是检查函数漏了「哪一条」「关键词」这些同义表达。教训是**改完先怀疑评测本身，再看模型**，否则会拿评测 bug 当模型问题反复改提示词。
- **一次差点误判的经历**：C09 的「重复调用」在单次全量运行里没复现，如果不是按任务要求做了 3 次重复，会误以为问题已经被指令修好。
